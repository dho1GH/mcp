# Moving `mcp` to the `itsjeff-os` organization

Assessment and runbook for transferring `dho1GH/mcp` to `itsjeff-os`.

## Recommendation

**Transfer the existing repository. Do not split it, and do not recreate it.**

GitHub's transfer moves issues, pull requests, stars, wikis, and full commit
history in one operation, and installs a permanent redirect from the old URL —
existing `git remote` entries and any links keep working. Creating a fresh repo
and pushing into it loses all of that.

The repo is small: **5.7 MiB packed** after this cleanup. There is no size or
LFS obstacle.

### Why not split into one repo per project

Splitting is tempting for 14 projects, but it is the wrong move here:

- Several projects share a lineage and are actively compared against each other
  (the three AutoGen runtimes, the two Hue Workers). Splitting freezes that
  comparison across repo boundaries.
- Path-filtered workflows already give you per-project CI, which is the main
  benefit people split for.
- 14 repos means 14 sets of secrets, rulesets, and Dependabot configs to keep
  in sync.

Revisit per-repo splits only for a project that gets external contributors or
its own release cadence.

## Blocking issue: third-party licensing

`graphiti_mcp_server/` appears to be a copy of the MCP server from
[getzep/graphiti](https://github.com/getzep/graphiti), which is **Apache-2.0**.
The repository has no `LICENSE` file anywhere and no attribution.

Apache-2.0 lets you redistribute, but requires retaining the license text,
stating your modifications, and shipping the license with the distribution.

**Keep the repository private until this is resolved.** Transferring to an org
is fine — the obligation is triggered by distribution, not by ownership. See
`graphiti_mcp_server/NOTICE.md` for the checklist. The cleanest fix is to
depend on the upstream package and delete the vendored copy.

## Security check

Both came back clean, which is what makes this transfer low-risk:

- **No `.env`, `.pem`, `.key`, or credential file has ever been committed**, on
  any branch, in the entire history.
- **No high-confidence secret patterns in history** — scanned all commits for
  OpenAI keys, GitHub PATs, AWS keys, Slack tokens, and private key blocks.

One low-severity note: the deleted 18 MB dump contained
`POSTHOG_API_KEY = 'phc_...'`. The `phc_` prefix is a PostHog *public project*
key, designed to ship in client-side code, and it belonged to the vendored
third-party repo rather than to you. No action needed, but it is a good
illustration of why the ignore rule for Repomix dumps is worth keeping.

## Transfer runbook

The transfer itself must be done by you through the GitHub UI — it cannot be
done over the API with the access this session has, and it requires org
ownership.

1. **Merge this branch first.** You want the cleanup and the `.gitignore` in
   place before org-level rulesets start enforcing anything.

2. **Transfer.** On `github.com/dho1GH/mcp` → Settings → General → scroll to
   Danger Zone → *Transfer ownership*. Enter `itsjeff-os`. You must be an owner
   of the org.

3. **Re-point local clones.** The old URL redirects, but update remotes anyway:
   ```bash
   git remote set-url origin https://github.com/itsjeff-os/mcp
   ```

4. **Add deploy secrets** at the org level so future repos inherit them:
   Settings → Secrets and variables → Actions →
   `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`.

5. **Create the `production` environment.** Settings → Environments → New →
   `production` → enable *Required reviewers* and add yourself. The deploy job
   targets this environment, so without it no manual deploy can run.

6. **Enable Actions.** Settings → Actions → General → allow all actions, and
   set workflow permissions to *Read repository contents*.

7. **Add a branch ruleset** on `main`: require a PR, and require the
   `graphiti_mcp_server (pytest + ruff)` and
   `federated-mcp-platform (vitest + tsc)` checks to pass.

## What the org actually buys you

- **Actions minutes.** Private-repo minutes go from 2,000/month on Free to
  3,000 on Team. The path filters matter more than the raw number — a one-line
  change to a Hue Worker runs one `tsc` job, not fourteen.
- **Environments with required reviewers.** This is the real unlock. Protected
  environments are not available for private repos on Free plans, and they are
  exactly what makes the gated deploy job safe.
- **Org-level secrets and rulesets**, shared across every repo you add later.
- **Dependabot** across all four ecosystems without per-repo setup.

## Known issues to fix after the move

1. **Worker name collision.** `hue-mcp-server/wrangler.toml` and
   `hue-mcp-server-v2/wrangler.toml` both declare `name = "hue-mcp-server"`.
   Deploying both publishes to the *same* Cloudflare Worker, each overwriting
   the other. Either rename v1's Worker or delete v1 now that v2 supersedes it.
   This is why deploys are manual and single-select.

2. **`federated-mcp-platform` has never been deployed** and provisions Durable
   Objects and a Workflow on first publish. Run `pnpm dry-run` and review the
   bindings before the first real deploy.

3. **Three test suites exist, and one of them cannot run.**
   `graphiti_mcp_server/tests/` (67 passing),
   `federated-mcp-platform/test/policy.test.ts` (12 passing), and
   `work-mamaz-main/test/capabilities.test.ts` — a real vitest suite covering
   capability grant matching and argument validation, which cannot execute
   because the project has no `package.json`. Everything else has no tests; the
   compile/typecheck jobs catch syntax and type errors but prove nothing about
   behavior. `nodered-mcp-server` is the most mature untested Worker and the
   best candidate for a first suite.

4. **`Zep_Temporal` does not compile.** `src/temporal/worker.ts` and
   `src/temporal/workflows.ts` both import `./activities.js`, which does not
   exist. Verified this is pre-existing and not caused by deleting
   `Archive.zip` — the zip contained the same file set as the tracked source,
   with no `activities.ts` in it either. The project is wired into CI as a
   non-blocking job so the breakage is visible without blocking merges.

5. **`work-mamaz-main` cannot be built at all.** There is no `package.json`
   anywhere at its root, and `wrangler.jsonc` sets `main = "worker/index.ts"`
   while `worker/` contains only `capabilities.ts`, `executors.ts` and
   `mcp.ts` — no entry point. It is therefore excluded from CI and from both
   deploy lists. It also declares five Workflows and a Durable Object binding,
   so it is substantial work that is currently unreachable. Restoring it needs
   an entry point and a manifest, not a CI change.

6. **`3dflat-affairs` carries duplicates that were not cleaned up.** Three
   files at the top level are byte-identical copies of files nested inside
   `flat-digital-twin-v2/`:

   | Top level | Identical to |
   |---|---|
   | `mcp-server-v2.ts` | `flat-digital-twin-v2/src/mcp-server-v2.ts` |
   | `spatial_graph_v2.json` | `flat-digital-twin-v2/spatial_graph_v2.json` |
   | `index.html` | `flat-digital-twin-v2/public/index.html` |

   Separately, `src/` holds a genuine v1/v2 lineage that should **not** be
   collapsed blindly: `mcp-server.ts` (424 lines) vs `mcp-server-v2.ts` (309),
   and `worker.ts` (84) vs `worker-v2.ts` (79). `wrangler.toml` builds
   `src/worker-v2.ts`, so v2 is live and v1 is the predecessor.

   These were left in place deliberately. The most recent commit on `main` is
   "Consolidate 3dflat-affairs and update live apps", which suggests the
   top-level copies may be an intentional partial consolidation rather than
   accidental duplication — that is your call to make, not one to guess at.

7. **`3dflat-affairs` fails `tsc` for a one-line config reason.** Its
   `tsconfig.json` sets `types: ["@cloudflare/workers-types"]` but leaves `lib`
   at the ES2022 default, which pulls in the DOM lib. The two definition sets
   clash on `Response`, `Element`, `EventListener` and ~60 others. Adding
   `"lib": ["ES2022"]` to `compilerOptions` should resolve it. Until then the
   project is excluded from CI.

8. **Two Workers carry placeholder bindings that will break a real deploy.**
   Both bundle fine, so `--dry-run` passes and the problem only shows up on a
   real publish:

   | Worker | Placeholder |
   |---|---|
   | `hue-mcp-server-v2` | KV namespace `AUDIT_LOG` is `REPLACE_WITH_KV_NAMESPACE_ID` |
   | `nodered-mcp-server` | `NODE_RED_BASE_URL` is `https://nodered.yourdomain.com` |

   Create the real KV namespace and set the real Node-RED URL before the first
   manual deploy. This is a good argument for keeping deploys gated.

9. **`pnpm-workspace.yaml` has unresolved placeholders** — `allowBuilds` entries
   literally read `set this to true or false`, which will need resolving when
   pnpm next prompts on those builds.

Two fixes came out of that verification and are baked into `ci-python.yml`:

- The graphiti suite needs `PYTHONPATH=tests`. `tests/` contains an
  `__init__.py`, making it a package, while two test modules import
  `test_fixtures` as a top-level module — so collection fails outright without
  it.
- `test_async_operations.py` requires a live `OPENAI_API_KEY` but is not marked
  `integration`, so `-m "not integration"` does not deselect it. It is ignored
  explicitly.
